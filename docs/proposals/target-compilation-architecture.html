1用户配置 · 原 DSL 对象

Target：平台与家族

选择 loader、游戏版本、mappings；组织 main / client / data / test，持有共用预应用开关。

MinecraftTarget · target.main查看共享范围

target 是平台 / 版本构建聚合。公开 target 上的 compilation 快捷入口仍代理 main，内部装配则显式写 target.main。

顶层 AW 是 main 的 AW 转发，并非给所有 compilation 的默认 AW。mixinPreapplication 则是具体 compilation 共用的 target Property。

改版本会影响整个家族，这是真实联系；不会复制版本状态来假装解耦。

2每 target 注册一次

平台游戏原料

Fabric 提供 Split(common, client)；Forge / NeoForge 提供 Joined(value)。共享原料，不共享清理结果。

registerFabricGame / registerJoinedGame查看原料与库接线

注册函数建立任务并返回 Provider、TaskProvider、Configuration 等句柄；此时不执行文件转换。GameShards<T> 是无行为的纯数据：Joined(value) 单片、Split(common, client) 双片，贯穿 named、AW、Strip 后文件及内部 Mixin 任务投影。joined 显式保留 loaderVersion Provider，不伪装成双片。

connectMinecraftLibraries 在原 init / construct 时点把共享库对齐 main 或独立 client 的原 runtime 配置；secondary 继承对应库，不重新逐一对齐。

库、metadata、patches / mappings 的接线仍在各平台原位置；图中的供料线不表示把这些都移入注册函数。

3每 compilation 独立

自己的源码与依赖

各有 SourceSet、原编译 / 运行配置、AW（访问权限调整）声明、Mixin 声明与输出。

main · data · test · client:data …查看独立性与 Linkage

这里的 AW 指访问权限调整；Mixin 声明是本项目资源，预应用输入则来自外部 compile mod，两者不是同一集合。

每个 compilation 有自己的开发结果、operation（预应用任务）与记录，不能借用 main 的 clean 游戏。

Common 共享源码并取参与者 API 交集；源码 linkage 与 stub classpath 是两条关系。它没有独立游戏 runtime，也不另造 Mixin operation。

Linkage 保留 C/R、include、AW/Mixins、outgoing 的成组关系；data 的 WITHOUT_DATA 和 test 输出例外继续显式处理。

来源：提案 §2、§5.3、§6.1

显式配对输入与出口

从家族取得自身 AW、target/main 原 AW、side、primary 与开关；直接组合窄函数。

compilation.setupFiles查看函数式边界

装配处知道双方关系；下层机制函数只收实际需要的值，不接整个 target / compilation 自由导航。原状态仍留 DSL、SourceSet、Task、Property 与 Configuration。

原位组合顺序：preview AW → 本地 runtime 辅助 AW → Mixin / Strip → sources；函数内部各管选择、注册或接线。

FinalJarTasks 在末端作为旧签名的兼容投影，与 consumption 来自同组结果；不存在第二条转换生产链。

取消全参数总入口 registerCompilationTransformations 作为内部主组织、由 setupFiles 原位直接组合的方向已获 ADR 接受；Mixin Spec 的职责、依赖图及 V3 已完成对应协调。必要旧签名仅作同组结果的兼容委托，具体 API 仍是候选，尚未实施或行为验收。

5开发视图 · 注册操作

自身 AW → Mixin 预应用

先调整游戏访问权限，再预应用外部 mod 的 Mixin；集中记录、清理与消费 state。

registerPreviewAw → registerMixinPreview查看 clean 如何产生

AW 输入为原游戏 + raw compile（上游原始视图）+ 本 compilation AW。Mixin 接原 AW 分片、外部 compile mod、raw compile/runtime 与平台库。

Mixin、records、Strip（清理）与原编译配置 state 必须由同一边界管理，避免记录和消费状态错配。AW 后句柄为 awGames；preview 输出为 strippedGames 与 operations 句柄。前者是 AW → Mixin → Strip 后的游戏，不代表 vanilla 或全部编译依赖。

CLIENT 处理两片：records 为 common → client，游戏查找 / 编译为 client → common；SERVER 保留 Split 静态注册，仅 common 进入有效游戏、operations 与 records，单元素有效列表不是 Joined；joined 一片。

预应用开启才选 Strip 后游戏；关闭使用原 primary AW + extra，原编译配置不安装本私有 state（包括 raw），必要 operation 直接为空且不读取本轮 operations。预先注册的任务可存在，不代表会执行。

来源：提案 §3（独立 client:data 逐阶段流）、§3.3、§7

6结果数据 · 不含行为

一次组成消费输入

有效外部 compile + 游戏 + 准备依赖；把开关、选片与文件生产依赖协议集中起来。

CompilationConsumption · preparation查看谁负责等待生产

producer 是“谁生产文件”的任务依赖。preparation 是保留原生 TaskDependency 的 FileCollection，覆盖有效非项目 compile 的文件 / Transform producer、有效游戏 producer 和必要条件 operation。

关闭也要保留外部 producer、AW 与正常 remap；不能只靠游戏任务间接携带依赖。

数据仅含有效外部 view、games、stubGames、preparation，不含方法、服务或 target 回引用。普通 games 关闭顺序为 primary → extra；stub 为 extra → primary。

此处集中协议，不代替 Gradle 对象状态；消费者不再判断 enabled、side 或枚举 records。首次生产与 Transform 参数隔离时机仍待动态验证。

来源：提案 §3.4、§6、§10

7开发链的实际消费者

编译 · 源码 · API · IDE

Java/Kotlin、sources、Common stub、sync 共用选择结果，各自在原位置接线。

registerGameSources · connect…查看四种消费方式
  • Java/Kotlin 等待 preparation；原 SourceSet / 项目身份与用户追加 classpath 保留。
  • sources 的 Decompile 复用已选主片及同一准备依赖，不重注册 preview；主片 primary 独立于 Mixin side。
  • Common stub 先选已有参与者，再投影其 consumption；保留 component 身份与参与者分组。
  • sync 要实际物化有效外部 compile、游戏和独立的原 runtime；下载 sources 时再依赖其 Provider。

Tooling 必须在同一请求显式 forTasks(":clocheIdeSync") 后取 model；裸 model 请求不会因有 Provider 就自动准备文件。

来源：提案 §3.4、§6.1、§6.2

8原链 · 独立出口

运行 / 发布用原输入

run / legacy 用原 runtime + AW / extra；发布用项目 Jar 链与 raw compile，不取 clean。

withCompilation · publicationClasspath查看 AW 差异与最终 JAR

runtime 辅助 AW 使用 raw compile + targetAW（main 转发）；独立 client 及其 secondary 的 runtime common 则引用 main 原 AW，与本 compilation preview AW 区分。

发布 classpath 为 raw 非项目 compile + 原项目 view + 原 AW / extra；最终项目产物沿 Jar → RemapJar（按 namespace）→ IncludeJar。游戏文件不是 outgoing mod JAR。

run / 发布不消费 preview clean / records；发布任务本身若依赖编译，仍可能随编译失败。平台 run 仍接 assets / natives / remap 或 patches / legacy。

来源：提案 §3.3、§5.2、§5.4、§7

主读线：1 配置家族 → 2 共享原料 + 3 自身状态 → 4 配对 → 5 开发转换 → 6 统一消费输入 → 7 消费。8 从原输入分出。箭头表示供料或接线，不表示函数同步处理完文件。

共享的是原料与平台事实

版本、平台库和家族关系保留联系；每个 compilation 自己注册 AW、preview 与 sources。

隐藏的是重复消费协议

开关、游戏选片与生产依赖集中一次；新编译器接准备依赖，无须了解 records 算法。

耦合留在真正需要的地方

setupFiles 配对输入；Mixin / records / state 共同维护；Linkage 保持成组关系及既有时序。

例：Fabric 独立 client:data 的 Java 编译

这是提案中的一条设计路径；用来区分配置期接线与执行期生产。

配置期创建对象与登记关系

  1. 1 · 构造 compilation

    共享 game 两片；自己的 SourceSet、编译 / 运行配置与 AW。runtime extra 指向 main 原 AW。

  2. 2 · setupFiles 注册

    本 compilation 的 AW → 本地辅助 AW（若有）→ Mixin / Strip → sources。这里只建立任务和 Provider。

  3. 3 · 返回，再发布

    平台库与 metadata 的必要接线在 construct 返回前完成；随后发布 value / isConfigured。

  4. 4 · 监听器，再用户 action

    依序接 feature、sync、buckets、编译与 Linkage 等；后配置值在合法首次解析前读取。

数据流：输入 → 输出句柄

Provider 描述将来取得什么；有效 view 保留依赖身份。

→
生产依赖：消费者 → preparation

dependsOn / builtBy 说明先准备什么；不能靠读取文件名反推任务。

执行期请求编译，依赖决定生产

  1. 1 · Java 任务等待准备

    preparation 包含完整有效非项目 compile 的原生文件 producer、游戏 producer 与必要 operation。

  2. 2 · 生产 clean 游戏与有效外部视图

    自身 AW 两片进入 CLIENT Mixin；records common → client，Strip 与消费 state 保持一致。游戏顺序 client → common。

  3. 3 · 消费开发 classpath

    保留原编译配置与项目身份，追加 clean client → clean common。必要 producer 失败则阻断编译。

本路径选择：clean client + clean common

sources 主输入为 clean client，clean common 作 library；不承诺一个 sources JAR 覆盖两片。

run 仍为自身原 client AW + main 原 AW common；发布仍沿原项目 Jar / raw compile 链。

执行期框表示生产与消费依赖，不是所有 Gradle 任务的强制串行调度。新增 preparation 的首次物化与 Transform 时机尚未实测。

进阶：side / primary、Common 回退与未决边界

Mixin side ≠ sources primary

Fabric 入口预应用 sidesources 主片
分割 main 及 data/testSERVERcommon
独立 client 及 data/testCLIENTclient
includedClient main 及 data/testCLIENTclient
未分割、未 includedClient main 及 data/testCLIENTcommon

CLIENT 两片转换，records common → client，游戏 client → common；joined 则是一片、CLIENT，没有独立 client compilation。side、primary 与开关各由 Provider 惰性决定，不因后配重新注册拓扑；原 primary/other 任务身份及命名保留，输出再惰性投影回 common/client。形状与 primary 不匹配时失败。

Common 选择与 run 回退不同

若独立 client 已存在但没有 data：Common client:data 回退该 client；run clientData 回退 target.data。缺所需 secondary 的 run 继续按原时点报错，不自动创建。

原依赖视图仍有精细区别

原 compile/runtime Configuration 分别简称 C/R。普通 raw 不等于完整 unmapped；后者分别从原 C/R 派生 raw + REMAPPED=false。角色交集不能重建完整 C/R，其精度 gap 尚未解决。

AW 的 remapPreparation 只在原 namespace 条件下接生产依赖，不是 AW 内容输入。raw 只向上游，clean 只向开发消费者，不回流 Mixin。

Feature / test 与迟到对象

非 test 沿原规则复用真实 Java main 变体或注册 feature；多 target 的 main 未必是 Java main。test 没有 outgoing feature / 归档任务。listener 对已有对象立即执行，迟到对象发布时执行，不统一推迟到“全部创建后”。

图示不能证明的部分

整体方案与 Joined/Split 泛型纯数据模型已接受；具体内部标识符、字段名与精确签名仍可调整，不冻结公开 API。旧 String/Map 仅在必要兼容边界校验标签、完整键集合及 primary/形状后单向适配同组结果，String 保留 common/client/joined 值；独立 runtime 辅助输入仍沿原协议，新链不逐阶段往返 Map。形状不证明字节阶段、producer 完整或任务已执行。新 preparation、Transform 首产 / 隔离、Tooling 实际物化、外部 JVM 使用与完整 ABI、缓存、性能及最终 IDE 导入未验证。转换失败沿原原因阻断，不增加失败后取 raw 的回退。
